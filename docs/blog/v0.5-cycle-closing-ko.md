# v0.5 cycle 마무리 — 11회 측정-주도 사이클이 남긴 것

> Lumen 빌드로그 #17. v0.5 전체 cycle 마무리 회고. 6주 동안 가설 → 측정 → 부정·확정
> 패턴을 11번 반복했고, 그 결과 격차는 1.376× → 1.304×로 좁아졌다. 그보다 더
> 가치 있던 건 직관 부정 사례 누적.

## v0.5의 한 줄 결산

- 멀티 스레드 격차: **1.376× → 1.304×** (Lumen 65 → 67 tok/s @ 8t)
- 단일 스레드: **Lumen이 ggml보다 +13% 빠름** (45.6 vs 40.4 tok/s)
- 측정-주도 사이클 **11회**: 명확한 perf win 2회 (8.A merge, 8.E.1 회복) + 정확한
  진단 1회 (8.D.5 N>1 codegen 비효율) + 회귀/부정 8회
- 인프라는 모두 살아 있음. AVX-512 ZMM, prefetch encoders, prefill plumbing —
  default-off 상태로 future host / future phase 대기

## 어떤 가설들이 부정됐는가

```
Phase 7.M  — Q8 native int dot product   → net-neutral
Phase 7.N  — VNNI single-acc             → -3.6%
Phase 7.O  — VNNI 4-acc                  → -2.7% (7.P에서 부활)
Phase 7.R/S/T — AVX-512 ZMM lane width   → -4.5%
Phase 8.B  — chunk L2-fit cap            → -3.5% (revert)
Phase 8.C  — software prefetch           → -49% @ 8t (revert)
Phase 8.D.3 — prefill batching plumbing  → -2.9× pp32
Phase 8.D.3 retro — "attention이 원인"   → 1%만 (false claim)
```

8개 부정 사례 + 1개 거짓 진단. 직관으로는 모두 합리적이었고 책에도 다 나와 있는
패턴이었다. ZMM이 256-bit YMM보다 빨라야 하고, 캐시 fit이 cache miss를 줄여야
하고, prefetch가 메모리 latency를 hide해야 하고, batching이 weight reuse를 살려야
한다. 측정 없이 갔으면 11번 사이클 중 절반은 잘못된 방향이었을 것이다.

## 측정으로 확정된 것

```
Phase 7.U   — 1.376× 격차의 정체 = 메모리 bw 활용 효율 차이 (Lumen 55% vs ggml 74%)
Phase 8.A   — atomic ThreadPool, +9% 1t, +3% 8t  → merge
Phase 8.D.5 — Q8 N>1 kernel은 N=1 × N보다 2.3-2.6× 느림   → 확정
Phase 8.E.1 — N=1 fan-out dispatcher로 prefill 회귀 회복 → +2.39× pp32
```

11번 시도해서 명확한 win 2개. 직접 짠 사이드 프로젝트로 ggml과 같은 차원에서
경쟁하면 이 비율이 정직한 거다. ggml은 5년+ 누적이라 매 시도가 win이기 어렵다.

## 가장 큰 발견 — single-thread Lumen이 ggml보다 빠르다

이 발견 자체가 v0.5에서 가장 의외였다. Phase 7.U에서 thread scaling 측정하다
1t 비교 row를 우연히 찍어보고 알게 됐다.

| Threads | Lumen | ggml | Winner |
|---|---:|---:|---|
| **1** | **45.6** | 40.4 | **Lumen +13%** |
| 2 | 60.8 | 62.5 | ggml +3% |
| 4 | 66.5 | 86.3 | ggml +30% |
| 8 | 67.4 | 87.9 | ggml +30% |

마이크로커널은 우리가 안 진다는 사실 — 5주 동안 다듬은 4-acc YMM + shape-aware
dispatch + Q8 native fused matmul + atomic ThreadPool. ggml의 1.376× → 1.304×
격차가 본질적으로 thread scaling 효율 차이라는 결론을 굳혔다.

이걸 알기 전엔 막연히 "ggml이 그냥 더 잘 짠 거"라고 받아들였는데, 측정해보니
어디서 격차가 발생하는지 정확히 짚을 수 있게 됐다. Phase 8.D는 이 사실 위에서
시작했다 — "memory bw 활용이 정체라면 weight reuse를 살리자". 그 가설도 부정
당했지만 (다른 이유로), 진단의 출발점이 정확했던 게 핵심이다.

## 메타 패턴 — commit message에 추측 적지 말 것

Phase 8.D.3 commit message는 이렇게 적었다.

```
The 2.9× regression is likely from the naive multi_head_attention's
O(seq²) cost dominating once we batch the matmul...
```

50줄 micro-bench로 24시간 안에 부정됐다. attention 비중은 0.66%였다. 측정 없이
추측한 commit message가 그대로 남으면 다음 사람(또는 future me)이 그걸 읽고
잘못된 방향으로 1주일 더 갈 수 있다.

규칙으로 만들었다: **commit message에 측정 안 한 추측 적지 말기**. 적어도 "추측
이지만 검증 안 됨" 명시할 것. 8.D.4 commit에서 그 다음 phase를 잡아냈고, 8.D.5
가 진짜 원인 찾았다. 만약 8.D.3에서 50줄 측정 먼저 했으면 1주 절약 가능했을 거.

## 인프라 폐기보다 default-off

11번 부정 사례 모두에서 코드는 살려뒀다. AVX-512 ZMM 인코더 12개, prefetch
인코더 3개, prefill plumbing (forward_layer_prefill_jit, Model::forward_prefill_jit,
chunked dispatch), chunk_rows L2 cap 헬퍼 — 다 main 브랜치에 있다.

폐기하면 future host(Intel Sapphire Rapids 같은 native 512-bit silicon)에서 ZMM
이 진짜로 win인지 다시 검증해야 한다. 또 future cycle에서 N>1 codegen이 재작성
되면 prefetch가 도움될 수도 있다. 측정 데이터 기반 default-off 정책이라
"무엇이 동작 안 했고, 어떤 조건에서 동작할 가능성이 있는지"가 코드로 남는다.

7.O의 4-acc YMM 인프라가 7.P에서 부활한 게 그 증거다. measure-driven 부정은
"버려라"가 아니라 "다른 조건을 기다려라"이다.

## v1.0까지 남은 마일스톤

[ROADMAP.md](../../ROADMAP.md)에 정리. 우선순위:

1. **Phase 8.E.2** — Q8 N>1 codegen rewrite. 7.G 4-acc 패턴 N>1 path 포팅. 8.E.1
   임시 fix 위에 진짜 가속. 3~5일.
2. **ARM64 backend** — Apple Silicon, Graviton, Raspberry Pi. AVX2 인코더만큼의
   작업량. 2주+.
3. **Q4 native matmul** — Qwen2.5-1.5B / 3B 실행 가능해짐. 2~3주.

각자 큰 사이클이고 또 측정-주도 패턴 반복 거의 확실. v0.6.0 / v0.7.0 / v0.8.0
순으로 단계 진행 가능. 사이드 프로젝트라 호흡이 일정치 않을 거.

## 마무리

Lumen은 v0.5.0 release-tagged 상태로 maintenance mode 진입한다. 메인 작성자는
다른 사이드 프로젝트로 호흡을 옮기는 중. 코드는 안정이고, 다음 cycle을 직접
시도해보려는 분이 있다면 위 [INDEX](./INDEX.md)의 11회 사이클 회고를 먼저
읽어보시는 걸 추천한다. 같은 함정을 반복하지 않게.

직접 짜본 사이드 프로젝트로 6주 동안 1.376× → 1.304× 격차 좁히고, single-thread
에서 ggml +13% 우위 확보, 11회 honest 사이클 누적. 사이드 프로젝트로는 이 정도면
잘 마쳤다고 본다.
