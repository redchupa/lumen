# 3장. DSL, AST, IR — 컴파일러의 세 단계

> 이 장에서는 컴파일러가 사람이 쓴 코드를 컴퓨터 명령어로 바꿀 때 거치는 세 단계를
> 다룹니다. DSL(언어), AST(구문 트리), IR(중간 표현). 추상적인 단어 같지만 사실은
> "한국어 → 일본어 번역 3단계"와 비슷한 구조입니다. Lumen 실제 코드의 짧은 예제로
> 직접 보면서 풀어 갑니다.

## 3.1 컴파일러가 하는 일

컴파일러는 한 문장으로 정리하면 **사람이 쓴 코드를 컴퓨터가 실행 가능한 명령어로
바꿔 주는 프로그램**입니다. Rust 컴파일러는 Rust 코드를 받아 기계어를 만들고,
Python 인터프리터는 Python 코드를 받아 (인터프리트 방식으로) 실행하고요.

그런데 컴파일러가 "Rust 코드 → 기계어"를 한 번에 통째로 변환하지는 않습니다.
중간에 여러 단계를 거칩니다. 각 단계마다 코드가 다른 형태로 표현돼요. 이 변환
과정을 한 마디로 풀면 **번역의 3단계**와 똑같습니다.

### 번역 3단계 비유

한국어 문장 "나는 학교에 갔다"를 일본어로 번역한다고 합시다.

1. **원문 단어 단위로 쪼개기 (Tokenize)**: "나는 / 학교에 / 갔다"
2. **문장 구조 파악하기 (Parse)**: 주어는 "나", 목적지는 "학교", 동사는 "가다(과거)"
3. **중간 의미 표현으로 정리 (Intermediate)**: [agent=나, target=학교, action=가다, tense=과거]
4. **목표 언어로 출력 (Codegen)**: "私は学校に行きました"

컴파일러도 똑같이 4단계를 거칩니다.

1. **렉서(Tokenize)**: 코드 문자열을 토큰 단위로 쪼갬. "fn", "matmul", "(", ")"
2. **파서(Parse)**: 토큰들을 트리 모양으로 정리 = **AST(Abstract Syntax Tree)**
3. **IR(Intermediate Representation)로 변환**: 의미만 남긴 추상 표현
4. **코드 생성(Codegen)**: 목표 아키텍처(x86_64, ARM64 등) 기계어로 출력

이 4단계는 모든 컴파일러가 본질적으로 같습니다. Rust, C, Go, Java 다 같은 흐름.
Lumen도 마찬가지입니다.

## 3.2 DSL — 우리만의 작은 언어

DSL은 **Domain-Specific Language**의 약자입니다. "특정 분야 전용 작은 언어"라는
뜻이에요. 일반 프로그래밍 언어(Rust, Python)와 달리 한 분야 일만 잘 표현하도록
설계된 언어입니다.

예를 들면 SQL은 데이터베이스 질의용 DSL이고, regex는 텍스트 패턴용 DSL이고, CSS는
스타일링용 DSL입니다. 일반 언어 안에서 그 일을 할 수도 있지만, DSL을 쓰면 그
분야를 훨씬 간결하게 표현할 수 있어요.

Lumen은 **텐서 연산용 DSL**을 만들었습니다. 매트멀, 활성 함수, 정규화 같은 LLM
내부 연산을 간단히 표현하기 위함입니다. 예시:

```
fn matmul(
    a: tensor<f32, [64, 128]>,
    b: tensor<f32, [128, 32]>,
) -> tensor<f32, [64, 32]> {
    return a @ b;
}
```

이 코드를 보면 몇 가지 특징이 있습니다.

- 함수 이름이 `matmul`
- 입력이 두 개의 텐서. 각각 `[64, 128]`, `[128, 32]` 모양
- 출력 텐서 모양 `[64, 32]`
- 함수 본문은 한 줄. `@` 기호로 매트멀 표현

Rust나 Python이 이걸 표현하려면 라이브러리를 임포트하고 dtype 클래스를 import하고
어쩌고 코드가 길어집니다. DSL은 이 한 가지 일(텐서 연산)만 잘 표현하도록 단어와
기호를 단순하게 했습니다.

### 왜 DSL을 직접 만드나

좋은 의문입니다. Rust나 Python을 그대로 쓰면 안 되나요? 가능은 합니다. 그런데
DSL을 만들면 다음 단계가 훨씬 쉬워져요.

- **타입에 텐서 형상이 들어감**: `tensor<f32, [64, 128]>`. 컴파일 시점에 매트멀의
  형상이 맞는지 검증 가능. `[64, 128] @ [128, 32]`는 OK지만 `[64, 128] @ [127, 32]`
  는 컴파일 에러.
- **표현이 단순함**: 분석할 코드가 단순하니 컴파일러도 단순해짐. Rust 컴파일러는
  100만 줄, 우리 DSL 컴파일러는 5천 줄.
- **다른 백엔드로 쉽게 변환 가능**: 같은 DSL 코드를 x86_64 매트멀, ARM64 매트멀,
  CUDA 매트멀 등 여러 목표로 변환 가능.

DSL의 가장 큰 가치는 **표현이 단순하므로 컴파일러도 단순하다**는 점입니다. 처음부터
짤 때 Rust 같은 거대 언어를 다루려고 하면 평생 가도 못 끝나요. 작은 DSL 하나로
시작해서 점점 확장하는 게 현실적인 길입니다.

## 3.3 AST — 코드를 트리 모양으로

DSL 코드가 한 문자열이라고 칩시다.

```
return a @ b;
```

이 문자열을 컴파일러는 토큰으로 쪼개고, 그걸 다시 트리 모양으로 정리합니다. 이
트리가 **AST(Abstract Syntax Tree)**입니다. 추상 구문 트리.

`return a @ b;`의 AST는 이런 모양이에요.

```
Return
  └── MatMul
        ├── Variable(a)
        └── Variable(b)
```

읽는 법: 최상위 노드가 "Return"이고, 그 아래 자식이 MatMul. MatMul의 자식은 두
변수 a와 b. 이 트리를 위에서 아래로 따라가면 "a와 b를 매트멀한 결과를 return
한다"가 됩니다.

더 복잡한 코드도 마찬가지로 트리가 됩니다.

```
return (a @ b) + c;
```

```
Return
  └── Add
        ├── MatMul
        │     ├── Variable(a)
        │     └── Variable(b)
        └── Variable(c)
```

### AST가 왜 필요한가

문자열을 그냥 두면 안 되나요? 두 가지 이유가 있어요.

**1. 트리가 분석하기 쉽다.** 문자열에서 "이 코드가 잘못된 부분"을 찾으려면 매번
다시 파싱해야 합니다. 트리는 한 번 만들어 두면 그 위에서 검사하고 변환하기
편해요.

**2. 변환할 때 정확하다.** "a @ b를 4×8 register tile로 변환"하려면 매트멀의 위치를
정확히 알아야 합니다. 트리에서 MatMul 노드를 찾는 건 명확한데, 문자열에서
"@"를 검색하면 다른 곳에 있는 @와 헷갈릴 수 있어요.

AST는 컴파일러의 "내부 표현 첫 번째 단계"입니다. 인간이 쓴 텍스트를 컴파일러가
다루기 좋은 형태로 첫 정리한 거예요.

## 3.4 IR — 한 단계 더 추상화

AST 다음 단계가 **IR(Intermediate Representation)**입니다. 중간 표현이라는 뜻인데,
조금 더 풀면 "의미만 남기고 표현은 단순화한 형태"입니다.

왜 또 다른 표현이 필요할까요. AST는 "사람이 쓴 코드의 구조"를 보존하고 있어요.
함수, return 키워드, 변수 이름 같은 게 다 들어 있습니다. 그런데 컴파일러가 코드를
변환할 때는 이게 다 필요 없어요. 필요한 건 "각 연산이 무엇이고 무슨 데이터를
받아 무슨 데이터를 만드냐"는 것뿐입니다.

이 핵심만 남긴 게 IR입니다.

### Lumen의 IR 예시

`return a @ b;`를 IR로 표현하면 이런 모양입니다.

```
%0 = Param(0)              : tensor<f32, [64, 128]>
%1 = Param(1)              : tensor<f32, [128, 32]>
%2 = MatMul %0, %1         : tensor<f32, [64, 32]>
     Return %2
```

각 줄은 하나의 연산을 표시합니다.

- `%0`, `%1`, `%2`는 **값의 이름**(SSA 형식이라 함). 한 번 만들어진 값은 다시 변경
  안 됨.
- `Param(0)`, `Param(1)`은 입력 매개변수.
- `MatMul %0, %1`은 두 입력을 매트멀.
- 각 값의 형상과 타입이 `: tensor<f32, [64, 32]>`로 명시됨.

이걸 AST와 비교하면 한 가지 큰 차이가 있어요. **AST는 트리(중첩 구조)**이지만
**IR은 평탄(flat list)**입니다. 모든 중간 결과에 이름이 붙어 있어요. 이 덕분에
"어떤 값이 어디서 사용되는지"를 쉽게 분석할 수 있습니다.

### IR의 진짜 가치 — 패턴 매칭

IR이 진짜로 빛나는 순간은 "여러 연산을 한 덩어리로 합치는 최적화"를 할 때입니다.
예를 들면 LLM에서는 이런 패턴이 자주 나옵니다.

```
%0 = Param(0)              : tensor<q8_0, [...]>     ← Q8 양자화 weight
%1 = Param(1)              : tensor<f32, [...]>      ← F32 activation
%2 = Dequantize %0         : tensor<f32, [...]>      ← Q8 → F32 변환
%3 = MatMul %2, %1         : tensor<f32, [...]>      ← 매트멀
     Return %3
```

이걸 그대로 실행하면 Q8 → F32 변환 한 번 하고 F32 매트멀 한 번 하는 두 단계가
됩니다. 그런데 패턴을 인식해서 **두 단계를 한 단계로 합치는 게 가능**해요. "Q8
weight × F32 activation = F32 output"이라는 융합 매트멀 커널을 만들면 변환을 따로
하지 않고 매트멀 안에서 한 번에 처리합니다.

Lumen은 이런 패턴 매칭으로 매트멀 자동 융합을 합니다(5장에서 자세히 다룸).
**같은 일을 더 빠르게 하는 핵심 기술**이에요. 이걸 AST로 하면 어렵습니다. AST는
트리 구조라 "Dequantize 다음에 MatMul"이라는 패턴을 찾기가 복잡해요. IR은 평탄
구조라 "%2의 op이 Dequantize이고 %2가 MatMul의 입력"이라는 조건을 단순한 코드로
검사할 수 있습니다.

## 3.5 단계별로 다시 보기

지금까지 본 세 단계를 한 코드의 흐름으로 정리합니다.

**원본 DSL 코드:**

```
fn matmul(
    a: tensor<f32, [64, 128]>,
    b: tensor<f32, [128, 32]>,
) -> tensor<f32, [64, 32]> {
    return a @ b;
}
```

**렉서가 토큰으로 쪼갬:**

```
[fn] [matmul] [(] [a] [:] [tensor] [<] [f32] [,] [[] [64] [,] [128] []] [>] [,]
[b] [:] [tensor] [<] [f32] [,] [[] [128] [,] [32] []] [>] [)] [->] [tensor]
[<] [f32] [,] [[] [64] [,] [32] []] [>] [{] [return] [a] [@] [b] [;] [}]
```

**파서가 AST를 만듦:**

```
Function "matmul"
  ├── Params
  │     ├── Param a: tensor<f32, [64, 128]>
  │     └── Param b: tensor<f32, [128, 32]>
  ├── ReturnType tensor<f32, [64, 32]>
  └── Body
        └── Return
              └── MatMul
                    ├── Variable a
                    └── Variable b
```

**IR로 lower:**

```
Function "matmul"(
    %0 : tensor<f32, [64, 128]>,
    %1 : tensor<f32, [128, 32]>,
) -> tensor<f32, [64, 32]>:
    %2 = MatMul %0, %1 : tensor<f32, [64, 32]>
    Return %2
```

**Codegen이 x86_64 어셈블리로 변환** (실제로는 더 복잡):

```
matmul:
    push rbp
    mov rbp, rsp
    # ... 매트멀 loop ...
    mov rax, [rdi]          # a 메모리 시작 주소
    mov rbx, [rsi]          # b 메모리 시작 주소
    # AVX2 SIMD 명령으로 8개 float 동시 처리
    vmovups ymm0, [rax]
    vfmadd231ps ymm1, ymm0, [rbx]
    # ...
    pop rbp
    ret
```

각 단계마다 표현이 점점 컴퓨터에 가까워지고 추상이 줄어듭니다. 사람 입장에서는
첫 단계(DSL)가 읽기 쉽고, 컴퓨터 입장에서는 마지막 단계(어셈블리)가 실행 가능
합니다. 컴파일러는 이 두 세계를 잇는 다리예요.

## 3.6 왜 4단계나 거치나 — 한 번에 안 되나

자연스러운 의문입니다. DSL을 곧바로 어셈블리로 바꾸면 안 되나요? 단계가 많을수록
코드가 복잡해질 텐데요.

이걸 한 단계로 만들 수는 있습니다. 그런데 두 가지 큰 문제가 생겨요.

**1. 백엔드별 분기가 어려워진다.** x86_64, ARM64, CUDA 세 종류 백엔드를 지원
한다고 합시다. DSL을 직접 변환하면 각 백엔드마다 DSL 파싱부터 어셈블리 출력까지
전부 다시 짜야 합니다. 3배 작업.

중간 IR을 거치면 DSL → IR은 한 번만 짜고 IR → 어셈블리 변환만 백엔드별로 짭니다.
공통 부분이 분리돼서 작업량이 훨씬 적어요.

**2. 최적화가 어려워진다.** 위에서 본 "Dequantize + MatMul → 융합 매트멀" 같은
최적화는 의미만 남은 IR에서 하기 쉽습니다. DSL 단계에서 하려면 문법 디테일에
파묻혀 패턴 매칭이 복잡해져요.

그래서 단계가 많은 건 코드를 더 복잡하게 만드는 게 아니라 **모듈 분리**해서
관리하기 쉽게 만드는 거예요. 처음 컴파일러 책을 펴면 단계가 너무 많아 헷갈리는데,
실제로 짜보면 "각 단계가 하는 일이 명확해서 디버깅이 편하다"는 걸 느낍니다.

## 3.7 Lumen 코드에서 실제로 어떻게 생겼나

실제 Lumen 저장소를 보면 다음 크레이트로 나뉘어 있습니다.

```
crates/
├── lumen-dsl/        ← 렉서, 파서, AST, 타입 검사
├── lumen-ir/         ← SSA IR 정의, IR 변환 패스
├── lumen-codegen/    ← x86_64, ARM64 코드 생성
├── lumen-jit/        ← 런타임 컴파일, 코드 캐시 (4장에서 다룸)
├── lumen-runtime/    ← 텐서, 메모리 풀, 디스패치
├── lumen-model/      ← GGUF 로더, 토크나이저, transformer
└── lumen-cli/        ← `lumen` 명령줄 도구
```

이 책의 1~3장이 끝난 시점에는 처음 세 개(dsl, ir, codegen)가 다 만들어졌다고
생각하면 됩니다. 다음 4장에서 lumen-jit이 등장합니다. 5장에서 lumen-codegen의
실제 어셈블리 출력 디테일을 더 보고, 6장 양자화는 lumen-runtime/lumen-model에
들어 있어요.

각 크레이트가 한 책임을 가지고 분리되어 있어서 한 분야씩 따로 이해할 수 있어요.
"내가 이번 주는 IR 패스만 본다"든가 "이번 주는 매트멀 codegen만 본다"든가가
가능합니다. 처음부터 끝까지 한 번에 다 이해하려고 하면 막막한데, 한 번에 한
크레이트씩 보면 관리 가능한 크기예요.

## 3.8 3장 핵심 정리

1. **컴파일러는 코드를 4단계로 변환한다**: 토큰(렉서) → AST(파서) → IR(중간 표현)
   → 어셈블리(codegen). 번역의 단계와 똑같은 흐름.

2. **DSL은 한 분야에 특화된 작은 언어**. 매트멀, 양자화 같은 텐서 연산만 표현
   하므로 단순. Rust 같은 거대 언어를 다루지 않아 컴파일러도 단순.

3. **AST는 트리, IR은 평탄**. AST는 사람이 쓴 코드의 구조를 보존하고, IR은 의미만
   남기고 분석·변환하기 좋은 형태로 단순화.

4. **IR의 진짜 가치는 패턴 매칭과 최적화**. "Dequantize + MatMul → 융합 매트멀"
   같은 변환을 IR에서 짧은 코드로 표현 가능.

5. **단계가 많은 이유는 모듈 분리**. 백엔드별로 따로 짜기 쉽고, 한 분야씩 관리
   가능한 크기로 쪼개기 위함.

## 다음 장 미리보기

4장은 **JIT(Just-In-Time 컴파일)**을 다룹니다. 일반 컴파일러는 코드를 미리 어셈블리로
바꿔서 파일로 저장해 두는데, JIT은 **프로그램이 실행 중일 때 그 자리에서 어셈블리를
만들어 메모리에 쓰고 즉시 실행**합니다. 이게 가능한 이유, 왜 LLM 추론 같은 분야에
유용한지, 메모리에 코드를 쓰는 게 무슨 의미인지를 풀어 봅니다. "컴퓨터가 자기
자신을 위한 코드를 짜는" 신기한 경험을 본격적으로 시작합니다.
