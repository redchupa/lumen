# 5장. SIMD — 한 명령으로 8개를 동시에 곱하기

> 이 장에서는 **SIMD(Single Instruction Multiple Data)**를 다룹니다. CPU가 한 명령
> 으로 여러 숫자를 동시에 계산하는 기술. 매트멀이 빨라지는 가장 큰 단일 요인이에요.
> AVX2, AVX-512 같은 단어가 등장하고, 한 명령어로 float 8개를 동시에 곱하는 신기한
> 동작을 직접 봅니다. 이 장이 끝나면 4장에서 다룬 어셈블리 인코딩이 SIMD에서
> 어떻게 활용되는지 자연스럽게 이어집니다.

## 5.1 일반 CPU 명령은 1번에 1개

먼저 일반 곱셈을 봅시다. CPU에게 "두 float을 곱해서 결과를 변수에 저장해라"라고
시키는 어셈블리는 이렇게 생겼습니다.

```
mulss xmm0, xmm1     # xmm0 = xmm0 * xmm1 (32비트 float 한 개)
```

`xmm0`, `xmm1`이 CPU의 **레지스터**라고 부르는 임시 저장 공간입니다. 한 레지스터에
한 숫자가 들어가요. 이 명령으로 한 번에 한 곱셈만 가능.

문제는 매트멀 계산할 때 곱셈을 엄청 많이 해야 한다는 거예요. 1장에서 매트멀 한
번에 약 870만 번 곱셈이 필요하다고 했죠. 한 번에 한 곱셈이면 870만 번 명령을
실행해야 합니다. CPU가 한 명령 처리하는 데 약 4 사이클 걸린다 치면 3500만 사이클.
3GHz CPU면 약 0.012초.

이걸 80% 줄일 수 있다면 어떨까요. SIMD가 바로 그걸 합니다.

## 5.2 SIMD — 한 명령에 여러 데이터

SIMD 명령은 한 명령으로 여러 데이터를 동시에 처리합니다. 예를 들어 AVX2의
`vmulps` 명령은:

```
vmulps ymm0, ymm1, ymm2     # ymm0 = ymm1 * ymm2 (32비트 float 8개 동시에)
```

`ymm0`, `ymm1`, `ymm2`는 256비트 레지스터예요. 32비트 float이 8개 들어갑니다.
이 한 명령으로 곱셈 8번을 동시에 처리해요.

매트멀에서 870만 번 곱셈이 필요하다고 했죠. SIMD로 한 번에 8개씩 하면 명령 횟수가
8분의 1, 약 110만 번. 같은 4 사이클이면 440만 사이클, 약 0.0015초. 8배 가속이에요.

이게 SIMD의 한 줄 요약입니다. **한 명령으로 8개(또는 16개) 데이터를 동시에 처리**.

### SIMD 레지스터 크기

x86_64 SIMD 레지스터는 세 가지 크기가 있습니다.

| 레지스터 | 크기 | float 32비트 몇 개 | 명령어 세트 |
|---|---:|---:|---|
| XMM | 128비트 | 4개 | SSE (1999년~) |
| YMM | 256비트 | 8개 | AVX/AVX2 (2011년~) |
| ZMM | 512비트 | 16개 | AVX-512 (2016년~) |

같은 CPU에서 다 사용 가능하지만 새 명령어 세트일수록 한 번에 더 많이 처리해요.
ZMM은 한 명령으로 float 16개. 이론상 XMM의 4배 가속이 가능합니다.

ARM도 비슷한 게 있어요. ARM의 SIMD는 **NEON**이라고 부르고, 보통 128비트(float 4개)
입니다. Apple Silicon 같은 ARM CPU는 NEON을 씁니다. 이 책의 핵심 코드는 x86_64
AVX2 위주이고, ARM64 NEON 지원은 향후 ROADMAP에 있어요.

## 5.3 SIMD가 빠르지 않는 경우

SIMD가 8배 가속이라고 했지만 항상 그런 건 아닙니다. 실제로는 여러 제약이 있어요.

**1. 데이터가 정렬돼 있어야 함.** SIMD 명령은 메모리에서 한 번에 8개를 읽는데, 그
8개가 연속된 메모리에 정렬돼 있어야 빠릅니다. 흩어져 있으면 별도 명령으로 모아야
하고 속도가 떨어져요.

**2. 같은 연산을 모든 데이터에 적용해야 함.** "8개 곱셈"은 가능하지만 "1개 곱셈
+ 7개 더하기"는 한 SIMD 명령으로 안 됩니다. 매트멀처럼 같은 연산이 반복되는
계산에 잘 맞아요.

**3. 분기가 없어야 함.** "if 양수면 곱하기, 음수면 더하기" 같은 분기는 SIMD가
약점. 8개 데이터 중 일부만 양수면 처리가 복잡해집니다. 매트멀은 분기가 없으니
SIMD에 적합해요.

**4. 메모리 대역폭이 충분해야 함.** SIMD가 8배 빠르게 계산해도 메모리에서 데이터를
가져오는 속도가 8배 빨라지지 않으면 무의미. CPU가 데이터를 기다리며 idle 상태가
됩니다. 1장에서 다룬 "메모리 병목"이 여기서 다시 등장.

요약하면 SIMD는 **연속된 데이터에 같은 연산을 반복하고, 분기가 없고, 메모리에서
빨리 가져올 수 있을 때** 가장 빛납니다. 매트멀은 이 4가지를 다 만족해서 SIMD의
가장 모범 사례 중 하나예요.

## 5.4 SIMD로 매트멀 짜는 기본 패턴

매트멀의 한 줄은 이렇게 생겼습니다.

```
out[k] = sum_{i} a[i] * b[i, k]    (i = 0..K-1)
```

K가 896이라면 곱셈 + 누적 896번. 일반 명령으로 짜면:

```rust
let mut acc: f32 = 0.0;
for i in 0..896 {
    acc += a[i] * b[i * N + k];
}
out[k] = acc;
```

SIMD로 짜면 8번씩 동시에 처리하므로 반복 횟수가 112번(896 / 8). 어셈블리는 이런
모양:

```
vxorps ymm0, ymm0, ymm0      # ymm0 = [0, 0, 0, 0, 0, 0, 0, 0]
loop:
    vmovups ymm1, [a + i*4]                  # a의 8개 float을 ymm1에 로드
    vfmadd231ps ymm0, ymm1, [b + i*4*N + k*4] # ymm0 += ymm1 * b의 8개 float
    add i, 8
    cmp i, 896
    jl loop
# ymm0의 8개 lane을 다 합쳐서 acc 만들기 (horizontal reduce)
vhaddps ymm0, ymm0, ymm0
...
```

`vfmadd231ps`가 매트멀의 핵심 명령입니다. **FMA(Fused Multiply-Add)**의 약자로
"곱셈과 덧셈을 한 명령에 처리"해요.

- 일반 SIMD: vmulps로 곱하고 vaddps로 더하면 2명령
- FMA: `acc = acc + a * b`를 한 명령

곱셈과 덧셈을 한 사이클에 처리하니까 또 2배 빨라집니다. AVX2 SIMD에 FMA를 더하면
스칼라 대비 약 16배 이론 가속 가능. 실제로는 메모리 병목 때문에 8배 정도가
실용 한계.

### Horizontal reduce — 8개 lane을 하나로

`vfmadd231ps`를 112번 반복하면 ymm0에 8개의 partial sum이 들어 있어요. 각 lane이
"전체 sum의 1/8"을 담고 있는 셈입니다. 이 8개를 하나로 합쳐야 최종 결과가 됩니다.

이 합치는 단계를 **horizontal reduce**라고 해요. AVX2에서 어셈블리는 좀 복잡합
니다.

```
vhaddps ymm0, ymm0, ymm0     # 옆 lane 끼리 짝지어 더하기
vhaddps ymm0, ymm0, ymm0
vextractf128 xmm1, ymm0, 1   # 위 128비트를 xmm1으로
vaddss xmm0, xmm0, xmm1      # 두 결과 합치기
```

이게 끝나면 xmm0의 첫 lane에 최종 합산 결과가 들어 있습니다. 이걸 `out[k]` 위치에
저장하면 한 column 완료.

복잡해 보이지만 4~5개 명령으로 끝나요. 한 column당 한 번만 하니까 inner loop에
비하면 작은 비용입니다.

## 5.5 4-Accumulator 패턴 — FMA 의존성 끊기

SIMD 매트멀을 짜면 한 가지 함정이 있습니다. 같은 accumulator(ymm0)에 계속 더하면
**FMA 명령이 직렬로 묶여요**.

```
vfmadd231ps ymm0, ymm1, ...   # 결과 ymm0 ← 4 사이클 대기
vfmadd231ps ymm0, ymm2, ...   # 앞 결과 기다림 ← 4 사이클 대기
vfmadd231ps ymm0, ymm3, ...   # 또 기다림
```

FMA 한 번이 4 사이클 걸리는데, 다음 FMA가 같은 ymm0를 사용하니 이전 결과를
기다려야 해요. 4 사이클 × N개 FMA = 4N 사이클. CPU의 FMA 처리량을 활용 못 함.

해결책: **4개의 독립 accumulator를 동시에 사용**.

```
vxorps ymm0, ymm0, ymm0     # 4개 모두 0으로 초기화
vxorps ymm1, ymm1, ymm1
vxorps ymm2, ymm2, ymm2
vxorps ymm3, ymm3, ymm3

# 32개 K 원소를 4 chunks (각 8개씩)로 나눠서 각 chunk가 다른 acc 사용
loop:
    vfmadd231ps ymm0, ..., [a + (i+0)*4]   # chunk 0 → ymm0
    vfmadd231ps ymm1, ..., [a + (i+8)*4]   # chunk 1 → ymm1
    vfmadd231ps ymm2, ..., [a + (i+16)*4]  # chunk 2 → ymm2
    vfmadd231ps ymm3, ..., [a + (i+24)*4]  # chunk 3 → ymm3
    # 4개 FMA가 서로 독립이라 병렬 issue 가능
    ...

# 마지막에 합치기
vaddps ymm0, ymm0, ymm1
vaddps ymm2, ymm2, ymm3
vaddps ymm0, ymm0, ymm2
# horizontal reduce
```

CPU가 4개 FMA를 거의 동시에 시작할 수 있어서 처리량이 약 2배 더 빨라집니다.
Lumen에서 이 패턴이 Phase 7.G에서 적용됐고, 매트멀 성능이 2배 가속됐어요(5.08
→ 17.97 tok/s, 1장의 측정 데이터).

### 왜 4개일까

이론적으로는 더 많은 accumulator를 쓸수록 의존성이 더 끊깁니다. 그런데 ymm 레지
스터는 16개로 제한돼 있어요. 일부는 매트멀 입력, 임시 변수 등 다른 용도로 써야
하므로 accumulator로 쓸 수 있는 건 4~8개 정도입니다.

또 FMA의 latency가 4 사이클이라 4개 acc면 그 의존성이 거의 다 끊깁니다. 더 늘려도
큰 추가 가속 없어요. 4가 sweet spot이라는 게 7.G 측정에서 확인됐습니다.

## 5.6 AVX-512가 항상 더 빠르지는 않다

상식적으로 AVX-512(ZMM, 16-lane)가 AVX2(YMM, 8-lane)의 2배 빨라야 할 것 같죠.
같은 일을 두 배 빨리 하니까요. 실제로 일부 Intel CPU(Sapphire Rapids 등)에서는 그런
패턴이 나옵니다.

그런데 **AMD Zen 4에서는 AVX-512가 오히려 4.5% 느렸어요**. 이게 Lumen v0.5
cycle의 Phase 7.R/S/T 측정에서 발견된 사실입니다.

이유: AMD Zen 4가 AVX-512를 내부적으로 256비트 두 번으로 쪼개서 실행하는
**"double-pumped" 구현**이에요. ZMM 명령이 두 µop(micro-operation)으로 쪼개져서
사실상 YMM 명령 두 번과 같습니다. 처리량이 늘지 않는데 EVEX 인코딩 오버헤드와
의존성 체인이 길어져서 오히려 손해예요.

이 사실은 AMD 문서 깊은 곳에 적혀 있긴 한데, 우리가 직접 짜고 측정하기 전에는
페이지를 펴 볼 이유가 없었어요. 2장에서 다룬 "직접 짜본 지식"이 정확히 이런 거
입니다. 책 100번 읽어도 안 보이고 측정해서 부딪쳐야 보이는 사실.

그래서 Lumen은 AVX-512 인프라를 다 갖춰 두고도 default-off 상태로 운영합니다.
Intel Sapphire Rapids 같은 native 512비트 silicon에서 측정해서 win이 확인되면
한 줄 변경으로 활성화 가능. 인프라 폐기 안 한 이유가 2장의 "다른 호스트에서
살아날 수 있다"는 패턴이에요.

## 5.7 SIMD를 직접 짜야 하나, 컴파일러가 해주나

마지막 의문 하나. Rust나 C 컴파일러는 자동으로 SIMD를 쓸까요? 일부는 그래요.
**자동 벡터화(auto-vectorization)**라고 부르는 컴파일러 최적화가 단순한 loop을
SIMD로 자동 변환합니다.

```rust
let mut acc = 0.0f32;
for i in 0..n {
    acc += a[i] * b[i];
}
```

이런 직선적인 loop은 LLVM이 자동으로 SIMD 변환 해줘요. 그래서 Rust release 빌드의
naive 매트멀이 이미 어느 정도 SIMD 활용 중입니다.

문제는 더 복잡한 패턴에서 자동 벡터화가 잘 안 되는 거예요.

- **4-accumulator 패턴**: 컴파일러가 의존성 체인 끊기 위해 4개 acc 쓰는 걸 자동
  으로 알기 어렵습니다.
- **양자화 매트멀 (Q8 unpack + dequant + multiply)**: 너무 복잡해서 일반 컴파일러는
  최적화 못 합니다.
- **레지스터 tile (4×8 등)**: 컴파일러의 일반적 자동 벡터화는 단순 loop만 봅니다.
  레지스터 tile은 사람이 직접 패턴을 만들어줘야 해요.

그래서 정말로 빠른 매트멀은 직접 인코딩해야 합니다. 사람이 머리로 패턴을 짜고
어셈블리 바이트를 손으로(또는 codegen으로) 만드는 게 가장 빨라요. Lumen은 이
부분을 codegen으로 자동 합성하니까 "사람이 한 번 짜면 형상별로 자동 적용"이 됩니다.

## 5.8 5장 핵심 정리

1. **SIMD는 한 명령으로 여러 데이터를 동시 처리하는 기술**. AVX2 YMM은 한 명령에
   float 8개, AVX-512 ZMM은 16개. 매트멀처럼 같은 연산을 반복할 때 8배 가속.

2. **FMA(Fused Multiply-Add)는 곱셈+덧셈 한 명령**. SIMD와 결합하면 한 명령에 8쌍
   곱셈+덧셈이 가능해서 매트멀의 핵심 명령.

3. **4-Accumulator 패턴은 FMA 의존성을 끊는 기법**. 4개 독립 acc를 번갈아 쓰면
   처리량이 약 2배 더 가속.

4. **AVX-512가 항상 더 빠르지는 않다**. AMD Zen 4는 double-pumped 구현이라 ZMM이
   YMM 두 번과 같음. 호스트마다 측정해야 안다.

5. **자동 벡터화는 단순한 loop만 처리**. 진짜 빠른 매트멀은 직접 인코딩 필요.
   Lumen은 이걸 codegen으로 자동 합성.

정수로 압축하면 메모리는 4배 줄어드는데 답이 똑같다는 게 어떻게 가능한지. JPEG
사진 압축과 비슷한 아이디어인데, 행렬에 어떻게 적용하는지를 풀어봅니다. Q8과
Q4의 차이, 그리고 양자화된 행렬을 SIMD로 빠르게 계산하는 트릭(VNNI 명령어)도
함께 등장합니다.
