# 2장. 왜 컴파일러를 직접 짜려고 했나

> 이 장에서는 LLM 추론 도구 표준(llama.cpp / ggml)이 이미 있는데도 처음부터 다시
> 짠 이유를 다룹니다. 효율로만 따지면 잘못된 결정이지만, 학습 자산으로 보면
> 옳은 결정이었다는 게 이 장의 결론입니다. 그리고 그 결론에 도달하는 길에서
> "책으로 배우는 지식"과 "직접 짜본 지식"이 어떻게 다른지, 사이드 프로젝트가
> 어떤 종류의 자산을 만들어 주는지를 함께 정리합니다.

## 2.1 이미 있는 표준 도구

LLM을 빠르게 돌리기 위한 도구는 이미 충분히 좋은 게 있습니다. **llama.cpp**가
대표적이에요. 내부 엔진을 **ggml**이라고 부르는데, 두 이름은 거의 같은 의미로
쓰입니다.

- 5년 이상 누적된 오픈소스 프로젝트
- C/C++ 기반, 거의 모든 운영체제와 CPU에서 동작
- 매트멀 커널이 양자화 × dtype × 형상별로 손코딩 되어 있어 매우 빠름
- 사용자 수가 많아 버그 빨리 잡힘, 새 모델 지원도 빠름

요약하면 **이미 최적화가 잘 되어 있는, 잘 작동하는 도구**입니다. 그런데 우리는
이걸 안 쓰고 처음부터 새로 짰습니다. Lumen이 그것입니다. 왜 그랬을까요.

## 2.2 효율로만 따지면 잘못된 결정

가장 먼저 인정하고 시작합시다. **목표가 "LLM을 빠르게 돌리는 도구를 만든다"는
거였다면 이건 잘못된 결정**입니다. llama.cpp를 다운로드 받아 쓰는 게 압도적으로
빠르고 안정적이에요. 우리가 6주 동안 짠 코드의 멀티스레드 성능은 llama.cpp의
약 77%(1.3배 격차). 6주 더 짜도 90% 따라가기 어렵습니다.

직접 짜는 게 효율로만 따지면 안 좋은 이유는 명확합니다.

- **시간**: 똑같이 동작하는 걸 만드는 데 6주 이상 들었습니다. llama.cpp 받아
  설치하는 데는 5분.
- **품질**: 5년 누적 코드를 단기간에 따라잡기 어렵습니다. 버그도 많고, 새 모델
  지원도 늦고, OS 호환성도 부족합니다.
- **유지 보수**: 우리만 쓰는 코드라 외부 PR로 개선될 일이 없습니다.
- **모험**: 같은 기능 만들면서 새 기능을 0개 추가했습니다.

이 4가지를 다 알면서도 짰습니다. 그 이유는 목표가 "도구"가 아니라 "**경험과
지식**"이었기 때문입니다.

## 2.3 책으로 배우는 지식과 직접 짠 지식

LLM 추론을 책으로 배운다고 가정해 봅시다. *Engineering a Compiler*(컴파일러 책),
*High Performance Computing*(고성능 컴퓨팅), llama.cpp 소스 코드 분석 글들, 양자화
논문 등을 다 읽는다고 합시다. 100시간 정도 읽으면 이런 지식이 머리에 들어옵니다.

- LLM은 매트멀이 95%
- SIMD는 한 명령으로 여러 데이터를 동시 처리
- 양자화는 fp32를 int8로 압축
- JIT은 런타임에 코드를 생성
- 어텐션은 시퀀스 길이의 제곱

100시간 후 이 지식이 머리에 있어도 다음 질문에 답하기 어렵습니다.

- "Zen 4에서 AVX-512가 YMM보다 빠르냐?"
- "VNNI 가속이 short K 매트멀에 win, long K에 loss인 이유?"
- "8 스레드 가속이 4배만 나오는 이유?"
- "prefill batching이 decode 32회보다 빨라야 하는데 왜 느려졌나?"

이 질문들은 책에 답이 없습니다. **직접 짜서 측정해야 답이 나옵니다**. 우리가 6주
동안 11번 가설을 세웠는데 그중 8번이 측정으로 부정당했어요(9장에서 자세히
다룸). 직관이 자주 틀린 분야라는 뜻입니다. 책 100번 읽어도 직관이 안 늘어나고,
한 번 직접 짜고 측정하면 그 직관 1개가 정확히 보정됩니다.

### "한 번 짜본 지식"의 구체적인 모양

추상적이라 한 가지 예를 봅니다. AVX-512 ZMM 명령어가 AVX2 YMM보다 2배 빨라야
한다는 게 책의 상식입니다. ZMM은 한 명령으로 16개 float을 다루고 YMM은 8개를
다루니까 단순 비례로 보면 2배 빨라야 합니다.

직접 짜고 측정해 봤더니 AMD Zen 4 CPU에서는 ZMM이 오히려 4.5% 느렸어요(7장에서
자세히 다룸). 이유: Zen 4가 AVX-512를 내부적으로 256비트 두 번으로 쪼개서
실행하는 "double-pumped" 구현이라서.

이 사실은 어디에도 안 적혀 있지 않습니다. AMD 문서를 깊이 찾으면 있어요. 그런데
**측정으로 부딪치기 전에는 그 문서 페이지를 펴 볼 이유가 없습니다**. 문제에
부딪쳐 봐야 정답을 찾으러 가게 돼요. 그래서 직접 짜본 사람은 책으로만 배운
사람과 같은 사실을 알아도 그 사실의 "맥락"을 압니다.

이 맥락이 사이드 프로젝트의 진짜 자산입니다.

## 2.4 사이드 프로젝트가 만드는 자산

직접 짜본 사람이 가지게 되는 자산을 정리하면 이렇습니다.

**1. 직관 보정.** 책의 상식이 어디까지 맞고 어디서 안 맞는지를 알게 됩니다. 11번
측정 중 8번 부정당하면 "직관은 자주 틀린다"가 체험으로 들어와요. 다음 프로젝트
시작할 때 측정 인프라부터 짭니다. 이게 안 짠 사람과 가장 큰 차이.

**2. 디버깅 깊이.** llama.cpp가 우리 컴퓨터에서 이상하게 동작할 때, 직접 짜본
사람은 어디부터 의심해야 하는지 압니다. 매트멀 형상이 안 맞는지, 양자화 변환이
잘못됐는지, CPU 명령어 호환성 문제인지. 사용자로만 써본 사람은 "왜 이래"로 끝나
지만, 짜본 사람은 한 단계 더 들어가요.

**3. 메타 패턴 누적.** 측정 → 부정 → 인프라는 유지 → 다른 조건 기다림. 이런
의사 결정 패턴이 누적됩니다. 이게 다음 사이드 프로젝트에서도 그대로 적용돼요.
완전히 다른 분야(임베디드, 분산 시스템, 무엇이든)에서도 같은 패턴이 작동합니다.

**4. GitHub 공개 자산.** 면접 자리에서 "이런 거 짜봤다" 할 수 있는 코드. 회고
블로그까지 같이 묶으면 "어떻게 의사 결정 했는지"도 보여줄 수 있어요. CV에 적힌
줄과 다릅니다.

**5. 동기 부여.** 책만 읽으면 6주째에 흐지부지됩니다. 작동하는 결과물이 매 commit
마다 늘어나는 게 동기 부여로 작동해요. v0.1.0에서 "안녕"이라는 한국어 토큰
하나가 컴퓨터에서 처음 나왔을 때의 감동이 기억에 박힙니다. 그 감동이 다음 phase의
연료가 되는 거예요.

## 2.5 그래도 효율은 효율이다 — 무엇을 포기하나

직접 짜기로 결정하면 포기하는 것들이 명확합니다. 이걸 미리 알아야 6주째에 후회
안 합니다.

- **production-ready 도구를 만들겠다는 욕심**: 5년 누적된 도구를 따라잡기 어렵
  습니다. 그건 인정하고 시작하세요. 목표는 "내가 이해한 LLM 추론"이지 "더 빠른
  llama.cpp"가 아닙니다.
- **빠른 결과**: 첫 commit이 의미 있는 결과를 내는 데 1~2주 걸립니다. 본격 가속이
  보이는 데는 3~4주. 매일 작은 진척만 누적될 거예요.
- **외부 사용자**: 우리만 쓰는 도구라 GitHub star 1000개 같은 건 어렵습니다. 그건
  곁가지로 두세요.
- **새 기능 추가의 즐거움**: 같은 기능을 다른 방식으로 만드는 거라, "이거 신기능
  추가했다" 같은 짜릿함은 적습니다. 대신 "이거 측정해 봤더니 직관이 틀렸다" 같은
  발견의 즐거움이 채워요.

이 4가지를 받아들이고 들어가야 흐지부지 안 됩니다.

## 2.6 Lumen이 결국 얻은 것

6주 작업의 정직한 결과를 미리 정리합니다. 이 책 후반부 chapter들에서 어떤
일들이 일어나는지 미리 그림이 잡힙니다.

- v0.1.0 → v0.5.0 (총 5번 release)
- 단위 토큰 생성 속도 약 15배 가속 (4.43 → 67 토큰/초)
- llama.cpp와 비교해서 8 스레드 격차 1.30배(쫓아가는 위치)
- **단일 스레드에서는 llama.cpp보다 13% 빠름** (의외의 발견)
- 측정-주도 의사 결정 11회 (가속 2, 진단 1, 부정 8)
- 회고 블로그 17편

이 중에 가장 큰 자산은 사실 **부정된 8번**과 **회고 블로그 17편**입니다. 가속
2번보다 이게 더 가치 있어요. 왜냐하면 가속은 다른 사람도 비슷한 패턴이 가능
하지만, 부정 사례 + 진단 패턴은 같은 분야에 한 번 직접 발 디뎌야만 얻는 자산
이거든요.

## 2.7 직접 짜는 게 안 맞는 상황도 있다

균형을 위해 반대 케이스도 짚고 갑니다. 다음 같은 상황이라면 직접 안 짜는 게
맞아요.

- **회사 일이 이미 비슷한 분야**: 매일 8시간 쓰는 분야를 또 사이드로 하면 호흡이
  빨리 무거워집니다.
- **결과물을 빨리 보여줘야 하는 상황**: 면접 마감 1달 같은 시점이면 직접 짜기보다
  llama.cpp로 데모 만드는 게 훨씬 빠릅니다.
- **목표가 학습이 아니라 도구**: 학습이 목표가 아니라 진짜로 빠른 LLM이 필요한
  거라면 직접 짜지 마세요. 도구를 잘 골라 쓰는 게 더 능력입니다.
- **이미 잘 알고 있는 분야**: 이미 잘 아는 걸 또 짜면 직관 보정이 안 됩니다. 잘
  모르는 분야로 가세요.

저는 회사에서 정보보안 일을 합니다. 컴파일러와 LLM 추론은 회사 일과 거리가 멀어요.
그래서 사이드로 적합했어요. 만약 백엔드 개발자라면 LLM 컴파일러보다 다른 사이드가
더 좋을 거예요. 사이드 프로젝트의 핵심은 **회사 일과 충분히 다른 분야**입니다.

## 2.8 2장 핵심 정리

1. **llama.cpp(ggml)이라는 표준 도구가 이미 있다.** 효율로 따지면 그걸 쓰는 게
   맞다.

2. **그래도 직접 짠 이유는 "지식과 경험"이 목표였기 때문**. 책으로 배우는 지식과
   짜본 지식은 깊이가 다르다.

3. **사이드 프로젝트가 만드는 자산**: 직관 보정, 디버깅 깊이, 메타 패턴, GitHub
   공개 자산, 동기 부여.

4. **포기해야 하는 것도 명확하다**: production-ready, 빠른 결과, 외부 사용자, 새
   기능 추가의 짜릿함. 이걸 받아들이고 들어가야 흐지부지 안 된다.

5. **모든 분야가 직접 짜기에 적합한 건 아니다**. 회사 일과 거리가 먼 분야, 학습이
   목표인 경우에 잘 맞는다.

## 다음 장 미리보기

3장에서는 본격적으로 컴파일러의 내부 구조로 들어갑니다. DSL, AST, IR이 정확히
뭐고 왜 필요한지. 컴파일러 책 펴면 첫 페이지부터 등장하는 이 단어들이 추상적이라
대부분 절반 못 가고 덮는데, Lumen의 실제 코드를 예로 들어 풀어 보면 의외로 단순한
개념이라는 걸 알게 됩니다.
